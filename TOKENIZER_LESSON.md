# Your first tokenizer: text → IDs → text

A language model works with numbers. A tokenizer converts text into a list of
integer IDs, and converts those IDs back into text. We can build this piece
before learning neural networks.

## Step 1: Give every byte an ID

Open `tokenizer/bpe.py` and look at `ByteBPETokenizer.__init__`.
Python's `text.encode("utf-8")` converts a string into bytes. Each byte is a
number between 0 and 255, which we use directly as its initial token ID:

```python
text = "banana"
raw = text.encode("utf-8")
print(list(raw))  # [98, 97, 110, 97, 110, 97]
print(raw.decode("utf-8"))  # banana
```

An emoji uses multiple UTF-8 bytes. That means a byte token need not be a whole
character. We reconstruct all bytes before decoding them into a string.

Three additional IDs are reserved: 256 is `<bos>` (beginning of a sequence),
257 is `<eos>` (end of a document), and 258 is `<pad>` (padding). They are added
explicitly with flags. Typing the literal text `<eos>` does not insert ID 257.
That makes ordinary text round-trip reliably.

**Try:** change `banana` to your name, a newline, or an emoji. Predict whether
the byte count and character count will match, then check.

## Step 2: Count neighboring pairs

Look at `count_pairs`. For `banana`, these byte pairs appear:

| Pair | Count |
|---|---:|
| `b` + `a` | 1 |
| `a` + `n` | 2 |
| `n` + `a` | 2 |

`zip(ids, ids[1:])` puts every ID beside the following ID. `Counter` counts
those pairs. Each training document is counted separately, so its final byte
cannot merge with the first byte of another document.

**Try:** count pairs in `aaaa`. You should see three adjacent `aa` pairs.

## Step 3: Learn one merge at a time

Look at `train` and `merge_pair`. The trainer chooses the most frequent pair
and assigns a new ID to its combined bytes. Ties use the smallest pair of IDs
so the result is reproducible. It then replaces occurrences and recounts pairs.
Future merges can combine the previously learned tokens into longer pieces.

For example, a token might first represent `an`, then another token might
represent `ana`. The next learned ID starts at 259. A vocabulary size of 280
allows at most **21 learned merges**, because 256 bytes and three special IDs
already occupy 259 slots. Training can stop earlier if no pair reaches the
minimum frequency.

Pairs can overlap while counting. In `aaaa`, the `aa` pair count is three,
but replacing pairs from left to right produces two `aa` tokens. Counting and
replacement are different operations.

This frequency-based algorithm is **byte pair encoding (BPE)**. Its learning
step uses counts; it has no neural-network weights or gradients.

**Try:** run `python3 -m tokenizer demo` and inspect the first eight merges.
The displayed token bytes make it possible to follow what each ID means.

## Step 4: Encode new text using the saved merge order

Look at `encode_bytes`. It starts with byte IDs, finds all currently available
learned pairs, applies the earliest learned pair, and repeats until no merge
applies. Encoding does not learn new tokens. It uses the vocabulary from training.

This is why unfamiliar words still work: every byte already has a base ID.
Spaces, punctuation, capitalization, and newlines are preserved. There is no
text normalization. Before merging, `encode` cuts the text into chunks (see
Step 7) and runs `encode_bytes` on each chunk separately.

**Try:** train on English text, then encode text containing an unseen emoji.
It may take more IDs, but decoding must reconstruct the same string.

## Step 5: Decode and save

`decode_bytes` replaces each ID with its byte sequence and joins those sequences.
`decode` converts the complete sequence back to UTF-8 text. Special IDs are
skipped by default. Unknown IDs are rejected.

`save` writes the ordered merges and special ID definitions to JSON. `load`
reconstructs the vocabulary. Keep a tokenizer with its model: ID 259 can mean
different bytes for different trained tokenizers.

An arbitrary token sequence generated by a future model can end halfway through
a UTF-8 character. Strict decoding will then fail; `decode(ids, errors="replace")`
is available for displaying such samples. Encoding and then decoding a valid
string remains exact.

## Step 6: Inspect the learned pieces

Run this after training the tiny tokenizer:

```sh
python3 -m tokenizer inspect --model models/tiny_tokenizer.json 'Hello, little robot!'
```

The output lists each token ID beside its bytes. The `b` prefix means Python is
displaying bytes. A leading space inside a piece is part of that token. For this
training file, the sentence splits into `H`, `e`, `llo`, `,`, ` little`, ` robot`,
and `!`. The ` little` piece starts with a space: a word keeps the space before
it. A token can represent part of a word or include a leading space.

Compare it with an unfamiliar sentence:

```sh
python3 -m tokenizer inspect --model models/tiny_tokenizer.json 'A spaceship visited Mars.'
```

Unfamiliar sequences can require more individual byte tokens. They still decode
correctly because the tokenizer already includes every possible byte. Compare
bytes per token rather than just token counts when the sentences differ in length.
This tells us about tokenization efficiency; it does not measure language-model
understanding.

## Step 7: Pre-split text into chunks

Without any splitting, BPE happily learns tokens like `e, t` or `. The` when
those byte runs are frequent. Each one wastes a vocabulary slot on a pairing
of a word with whatever happened to sit next to it. GPT-2 fixed this by cutting
text into chunks first and only merging *inside* a chunk.

Look at `GPT2_SPLIT_PATTERN` and `pre_split` in `tokenizer/bpe.py`. The pattern
tries these branches in order at each position:

| Branch | Matches | Example |
|---|---|---|
| Contraction | `'s`, `'t`, `'re`, `'ve`, `'m`, `'ll`, `'d` | `it's` → `it` + `'s` |
| Letters | an optional space, then letters | ` world` |
| Digits | an optional space, then digits | ` 2026` |
| Other | an optional space, then symbols, including `_` | `,` or ` !?` |
| Whitespace | spaces, but leaving one for the next word | `a   b` → `a`, `  `, ` b` |

```python
from tokenizer.bpe import GPT2_SPLIT_PATTERN, pre_split
print(pre_split("Hello world, it's 2026!", GPT2_SPLIT_PATTERN))
# ['Hello', ' world', ',', ' it', "'s", ' 2026', '!']
```

The standard `re` module has no "letter" class, so `[^\W\d_]` builds one: a
word character (`\w`) that is not a digit or underscore. Every character falls
into some branch, so joining the chunks always gives back the original text,
and `test_chunks_join_back_to_original` checks this on random Unicode.

Training treats every chunk like a tiny separate document, which is why the
same `count_pairs` code still works. `encode` must split the same way, so the
pattern is saved in the tokenizer file (format version 2). Old version 1 files
load with `pattern=None`, meaning no splitting.

**Try:** train the tiny corpus twice, once with `--no-pre-split`, and compare
the learned pieces with `inspect`. Which tokens in the unsplit version cross a
word boundary?

## Step 8: Make training fast without changing the answer

The trainer in Step 3 recounts every pair in the whole corpus before each
merge. For 1,000 merges on 0.5 MB of text it takes about 60 seconds; a 32k
vocabulary on hundreds of megabytes would take weeks. That simple version is
still in the code as `learn_merges_reference`. The fast `learn_merges` uses
three ideas:

1. **Count each distinct chunk once.** After pre-splitting, a corpus is mostly
   repeats: ` the` might appear a million times. We keep a `Counter` from each
   distinct chunk to how often it appears, and every pair inside it counts with
   that weight. 36 MB of Python source has only about 100,000 distinct chunks.
2. **Update counts instead of recounting.** Merging `a`+`b` only changes chunks
   that contain `a b`. The dictionary `where` remembers which chunks hold each
   pair. For each of those chunks we subtract its old pairs and add its new ones.
   Every other count is still correct.
3. **Use a heap to find the best pair.** `heapq` always gives the smallest
   item, so we store `(-count, pair)`: the largest count comes out first, and
   equal counts give the smaller pair first, the same tie rule as before. When a
   count changes we push a new entry and leave the old one in the heap; an entry
   popped with an out-of-date count is skipped.

The reference version is the **test oracle**. `FastTrainerTests` trains both on
the tiny corpus and on 60 random corpora full of ties and runs like `aaaa`, and
requires identical merges and counts. With that check, you can keep optimizing
without worrying that you changed what is learned.

| Corpus | Merges | Reference | Fast |
|---|---:|---:|---:|
| 0.5 MB Python source | 1,000 | ~60 s | 0.1 s |
| 36 MB Python source | 32,509 | (too slow to run) | ~6 s |

**Try:** in `learn_merges`, remove the `continue` that skips stale heap entries
and run the tests. Which test fails, and why?

## Step 9: Make encoding fast

To feed the model, we must encode about 9 GB of text once. The simple encoder
ran at about 1.5 MB/s, which is close to two hours, and every bug fix means
doing it again. Two changes, measured on a 32k tokenizer and an M4 with 10 cores:

1. **Cache each chunk's IDs** (`_encode_chunk`). Encoding a chunk always gives
   the same IDs, and the same chunks (` the`, `,`, ` of`) repeat constantly, so
   we look them up in a dictionary instead of re-running the merges. To bound
   memory, the dictionary is emptied when it reaches `CHUNK_CACHE_SIZE`; common
   chunks come back almost immediately. **1.5 → ~10 MB/s.**
2. **Use every CPU core** (`encode_many`). Python runs one thread of Python
   code at a time, so we start separate *processes*. Each builds its own
   tokenizer and cache once, then encodes whole documents; `imap` returns the
   results in the original order. **~50 MB/s on 55 MB of text**, so 9 GB in
   about 3 minutes. On small inputs, starting the workers costs more than it
   saves.

Tests check that the cached encoder gives exactly the IDs the uncached one
gives (with a tiny cache, so clearing is exercised) and that `encode_many`
matches `encode` document by document.

Measure the result against a real tokenizer with `scripts/bench_tokenizer.py`.
It reports **bytes per token** on held-out text (higher means each token
carries more text, so the model sees more text per step), speed, and exact
round-trips on tricky strings like emoji sequences and Windows newlines.

**Try:** run `python3 -m cProfile -s cumtime` on a script that encodes a few
megabytes with the cache cleared every call. Where does the time go?

## Step 10: Train on real data and compare with GPT-2

`scripts/sample_fineweb.py` downloads part of FineWeb-Edu, educational web
pages filtered for quality. The data is stored as parquet files of about 2 GB
each, split into *row groups* of 1,000 documents, so the script reads only
evenly spaced row groups over HTTP. Training documents come from one file and
held-out documents from another: a tokenizer measured on text it was trained on
looks better than it really is. The manifest records the exact dataset
revision, so anyone can rebuild the same sample.

The result, on 25 MB of held-out text: **4.63 bytes per token with 32,768
IDs, against GPT-2's 4.64 with 50,257.** Compare how both split one sentence:

```text
ours:  Phot | osynt | hesis | ␣converts | ␣sunlight | ... | ␣chlor | oplast | s | .
gpt2:  Photos | ynthesis | ␣converts | ␣sunlight | ... | ␣chlor | opl | asts | .
```

Common words are single tokens in both; rare words break into pieces. The
last merges ours learned (` firsthand`, ` remission`, ` preterm`) show what an
educational corpus is about.

**Be honest about the comparison:** ours was trained on the same kind of text
it is tested on; GPT-2's tokenizer was trained on different web text. A fair
summary is "matches GPT-2's compression on FineWeb-Edu with a smaller
vocabulary", not "beats GPT-2".

**Try:** train vocabularies of 8k, 16k and 32k on the same sample and plot
bytes/token against vocabulary size. Where do extra IDs stop paying off?
